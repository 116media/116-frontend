# 12 — Internationalisation

Namespaces, the complete key inventory, and the plural rules the counts depend on.

> **Scope history.** This inventory covered three tabs, grew to cover merch and tour, and is now
> back to **three tabs over five content surfaces** — merch, tour and featured credits were all cut
> ([07](07-artist-detail-tabs.md), [08](08-catalog-sections.md)). What survives: the identity block,
> the social row, the four `Musique` sections, and the reversal of the **"never Top/Populaires"
> rule** — the profile ranks, honestly.

## Namespaces

### `artists` — the module namespace

A new module bundle, registered in `shared/presentation/i18n/resources.ts` alongside
`articles` / `videos` / `shorts`:

```text
src/modules/artists/presentation/i18n/
├── index.ts                      → export const artistsMessages = { en, fr }
└── locales/
    ├── en/{index.ts, directory.ts, profile.ts, common.ts}
    └── fr/{index.ts, directory.ts, profile.ts, common.ts}
```

Each locale `index.ts` spreads the area files, so keys resolve flat under the module key:
`t("artists.card.contentCount", { count })`.

Four files, split by route rather than by surface. An earlier version added a file per late-landing
surface; with merch and tour cut, `profile.ts` covers the whole profile route and the split would
be ceremony.

The namespace key is **`artists`**, not `artistes`. The *route* is French and locked
([01](01-overview.md)); the *module* follows the codebase's English module naming
(`videos`, `articles`, `shorts`). Mixing the two would give `t("artistes.…")` inside
`modules/artists/` — a mismatch every reader has to re-learn.

### The existing shared `artistes` namespace becomes obsolete

[`../lyrics-page/04-routes-and-artist-placeholder.md`](../lyrics-page/04-routes-and-artist-placeholder.md)
specifies a small shared `artistes` namespace holding `pageTitle`, `comingSoon.title` and
`comingSoon.subtitle` for the placeholder page. This feature replaces that page, and those three
keys have no other consumer — they are deleted in the same commit that ships the index route, from
**both** locale catalogs.

> **Found while checking:** neither the shared `artistes` namespace nor
> `app/(public)/artistes/page.tsx` exists in the repo today. The lyrics-page doc describes them as
> planned, not shipped. If the placeholder still hasn't landed when this feature starts, the
> "removal" is a no-op and the placeholder should simply never be built.

## Plural counts — the part that must not be shortcut

Every key that renders a number and a noun needs i18next's plural suffixes, **not** string
interpolation into a hardcoded plural. The profile adds three more of them — the release, video
and article count entries:

```ts
// fr
contentCount_one: "{{count, number}} contenu",
contentCount_other: "{{count, number}} contenus",
```

```tsx
t("artists.card.contentCount", { count: artist.contentCount });
```

Rules that make this work:

- The variable **must be named `count`**. i18next selects the `_one` / `_other` suffix from
  `Intl.PluralRules` on that specific key; passing `total` or `n` silently returns the base key and
  the plural never resolves.
- **Both suffixed forms are always written, in both locales**, even when they are identical (French
  `{{count}} min de lecture` in the articles catalog does exactly this). Omitting `_other` because
  it looks like a duplicate breaks the moment the copy changes.
- **`{{count, number}}`, not `{{count}}`.** i18next v26 ships the `Intl.NumberFormat` formatter by
  default, which is what produces `1 234` in `fr` and `1,234` in `en` — the locale-formatted numbers
  [06](06-artist-detail-hero.md) requires. Bare `{{count}}` prints `1234` in every locale.
- **No `_zero` forms are needed.** French treats 0 as `one` (`0 chanson`), but no zero ever reaches
  these keys: the index lists only artists with ≥1 item ([04](04-artists-index-page.md)), the hero
  omits zero stats rather than rendering them ([06](06-artist-detail-hero.md)), and every empty
  section or tab is hidden rather than counted ([09](09-loading-empty-error.md)). With merch and
  tour cut, the one case that used to look like an exception — a tour tab with no upcoming dates —
  is gone too, so the rule now holds without qualification.
- Components never assemble sentences. `"{{count}} " + t("songs")` is not a translation.

## The hard rule

`fr` and `en` must hold **the exact same keys, in the same commit**. `resources.ts` derives the
canonical key shape from the English catalog and feeds it to the react-i18next type augmentation,
so a key present in one locale and missing in the other is a type error — but a key added to *both*
with only one translated is not, and that is the failure mode to watch. French is the fallback
locale; an untranslated English key silently renders French to an English reader.

The condition that breaks it is a surface landing long after the rest — `Actualités` waits on
Gap 5, and releases on Gaps 3 and 4 ([16](16-backend-gaps-and-contracts.md)). Whichever locale file
those keys land in, they land in **both** locales in the same commit as the component that reads
them, or not at all.

### Corrected — the profile does rank, so the label may say so

> This doc previously stated: *"Section headings are never 'Top' / 'Populaires' — we sort by date,
> and 'Dernières' is the only label that's true."* **That is now wrong** and is reversed here.
> `LyricsEntity` carries `ViewCount` and `GET /public/lyrics` already supports `sort=views`
> ([16](16-backend-gaps-and-contracts.md)), so the profile ranks on real data
> ([07](07-artist-detail-tabs.md), [08](08-catalog-sections.md)).

The rule survives in a stricter, more useful form:

**A section's label must name its actual sort key.** Not "never rank" — *never mislabel*.

That makes exactly one heading in this feature a ranking label, and its wording is not free:

| Key | `fr` | `en` |
|---|---|---|
| `sections.popular` | **Les plus lues** | **Most read** |

- **Not *"Les plus écoutées"***, which is the phrase that reads most naturally in French and is a
  lie. We count **reads** — `ViewCount` on a lyrics page — not plays. Nothing on 116 streams audio
  ([01](01-overview.md)), so "most listened to" claims a metric we do not have and could not
  produce. This is the exact failure the original rule existed to prevent; the rule now catches it
  at the wording level instead of banning the section.
- **Not "Top 10"**, **not "Populaires"** as the sole label either — both describe a vibe rather than
  a metric, and "popular" invites the reader to assume likes or shares are in the mix. They are not
  ([08](08-catalog-sections.md)): the sort is `ViewCount` alone.
- `lues` is feminine plural agreeing with *chansons*. If the heading is ever reworded to a
  masculine noun the agreement changes — this is a translation, not a token swap.
- The index deliberately has **no** ranking label at all ([01](01-overview.md) decision 6): it is a
  directory, ordered A–Z, and no honest popularity signal exists across artists.

`states.emptyLetter.title` and `states.emptySearch.title` reproduce the copy already specified in
[05](05-alphabet-search-and-filters.md), including the French guillemets. Keep the guillemets in
`fr` and straight quotes in `en` — this is exactly the kind of detail that gets flattened when a
translation is copy-pasted between locales.

`states.notFound.body` covers both 404 causes in one sentence ([09](09-loading-empty-error.md)).
Splitting it into two variants would leak *why* the page is missing, and "this artist exists but
has nothing published" is internal information. Its wording — *"n'a pas encore de contenu publié"* —
is deliberately surface-agnostic and stays correct now that "content" means any of the five
surfaces ([01](01-overview.md) decision 4, as corrected).

`a11y.socialLink` **reverses word order between locales** (`{{platform}} de {{name}}` vs
`{{name}} on {{platform}}`). That is the point of putting it in a translation file: a component that
concatenated `platform + " de " + name` would produce "Instagram of Fally Ipupa" in English word
order forever. Both interpolations must appear in both locales or the name loses half its content.

## URL values are never translated

`?tab=music|videos|news` are **stable English keys**, locked in [07](07-artist-detail-tabs.md).
The same applies to `?letter=` values, the `#` bucket, and the `Musique` section anchors
`#popular` `#latest` `#albums` `#mixtapes`.

> **Corrected.** This section previously enumerated `?tab=lyrics|videos|albums`, then
> `?tab=…|merch|tour`. The keys `lyrics`, `albums`, `merch` and `tour` are all **retired**
> ([07](07-artist-detail-tabs.md)) and nothing shipped any of them, so no redirect is owed. If one
> turns up in a shared link, `lyrics → music` and `albums → music#albums` are the correct
> mappings; everything else falls through to the default-tab rule.

Only the tab *labels* come from `tabs.*` and the section labels from `sections.*`; the values are
constants in the module's `constants/`, and there is **no locale-keyed map between them**. This
matters because `Musique`/`Music` are near-identical across locales, which makes a "just use the
label" shortcut look harmless right up to `Actualités`/`News`. A URL that changes meaning with the
reader's language cannot be shared, bookmarked, or canonicalised ([13](13-seo-and-metadata.md)).

The same rule binds the anchors. They are constants, never slugified from the translated `<h2>`
text — a fragment derived from `Dernières chansons` would give `#dernieres-chansons` in `fr` and
`#latest-songs` in `en`, so a shared deep link would scroll nowhere for half the readers.

## Reused keys

Nothing in this feature duplicates a shared key. `general.metaTitleDefault` and
`general.metaDescription` remain the site-wide fallbacks used by
[13](13-seo-and-metadata.md); the navigation label for the header's "ARTISTES" link stays in the
existing `navigation` namespace and is not moved into this module.
